# 0007 — Review fixes

Date: 2026-11-01. Work from the external review ("Stage Ready (GrillMe) — Review, Score & Improvement Prompt", 49/75), phase by phase. No stack changes. ## Phase 1 · Judges can try it in one click

1. **Guest Demo Mode.** `POST /api/demo` works signed out: it creates a guest user (`users.is_guest`), sets a signed httpOnly cookie (`sr_guest`, HMAC-SHA256 with `AUTH_SECRET`, 24 h, `SameSite=Lax`, `Secure` in production), seeds Signal Garden for it and redirects. `getCurrentUser()` falls back to the cookie after the GitHub session, so every existing ownership check applies to guests unchanged. Guest creation is rate-limited to 5 per IP per hour; guest users and their projects are deleted 48 h after creation (on the next guest creation). Guests cannot create projects, link repos or turn on cloud upload (`route(..., { guests: "…" })` answers 403 `guest_forbidden` with a sign-in hint); the app shell shows a banner with a Sign in button. DEV_AUTH_BYPASS still wins locally.
2. **No raw JSON on navigations.** `route()` detects browser navigations (`Sec-Fetch-Mode: navigate`, or `Accept: text/html` without fetch metadata): 401 redirects to `/signin`, other errors to `/problem?message=…`, a branded page. `fetch()` callers still get JSON.
3. **Real Meta models in Demo Mode.** `createDemoAi()` wraps the live adapter in `BudgetedLLM`: Demo Mode keeps its scripted speech and fixtures, but claim extraction and verification, judge turns, show-or-strike, Coach Notes and the question bank run on Muse Spark and Muse Wonder. Spend is shared across web, realtime and the worker through Redis (`demo-ai:calls:<day>`, `demo-ai:usd:<day>`, UTC days). Real calls stop for the day at `DEMO_DAILY_CALL_LIMIT` (default 1500, always enforced) or `DEMO_DAILY_BUDGET_USD` (default 5, only for models priced in `MODEL_PRICES`, since Meta's prices are not in the repo); then the prompt's mock answers and the result carries `fallback: "budget"`. A failed real call also falls back to the mock (`fallback: "error"`), so a demo never breaks in front of a judge. `DEMO_LIVE_MODELS` defaults to true in production and false elsewhere, so local runs and CI stay deterministic. Muse Image card art stays off in Demo Mode (fixture renders stay reproducible), as does hosted SAM (DemoGuard's Demo Mode scenario relies on the local tracker).
4. **Model attribution.** `ledger.update` and `judge.speak` carry `model: { modelId, latencyMs, fallback? }`; claims, judge turns, questions and Coach Notes store `model_id` and `model_latency_ms`. Captions read "Muse Spark 1.3 · 1.9 s", "Mocked", or "Mocked · today's demo allowance is used up" (`modelCaption` in `packages/shared`). A claim's caption names the model behind its current verdict: extraction, or the later verification or show-or-strike call; deterministic rule verdicts keep the extraction caption, and their evidence shows the rule.
5. **Brand.** The review's icon set: `src/app/icon.svg`, `favicon.ico`, `apple-icon.png`, `manifest.ts`, `public/icon-192.png` and `icon-512.png`, and `StageReadyMark` replacing the Sparkles tile on the landing page, the sidebar, the sign-in page, the problem page and the cold-start page.
6. **Sign-in page.** `/signin` (Auth.js `pages.signIn` and `pages.error`): the mark, the tagline, Continue with GitHub, "Read-only repo access; Stage Ready never writes to your repo", and Try the guest demo. `callbackUrl` must be a same-site path.
7. **Landing clip.** The review asked for a clip rendered with the Director from the Demo Mode project, but Demo Mode's fixture takes are labelled colour bars, which show nothing of the product. The clip is instead recorded from the real app in Demo Mode by `pnpm --filter @stage-ready/web clip` (Playwright per scene, then FFmpeg: trim, burned captions, 0.4 s crossfades): one click into the demo, a rehearsal where the Claim Auditor contradicts "instant", the Q&A Kit, the Director and DemoGuard. 19.4 s, 1280×720, 380 KB, with a poster frame; it autoplays muted and loops in the hero.
8. **Cold start.** The router answers browsers with a branded "Waking up Stage Ready…" page (503, refreshes every 5 s, light and dark) and API callers with JSON 503 and `Retry-After`. `start.sh` opens the public port only once web and realtime answer, so Modal, which waits for the port, holds the first request instead of showing that page at all in most cold starts. `KEEP_WARM=1 modal deploy …` sets `min_containers=1`.

Tests: guest cookie signing (web unit), the demo allowance and `createDemoAi` (ai), captions (shared), model tags on live messages (realtime), and `e2e/guest.spec.ts` on a second dev server without the auth bypass (signed-out landing → Signal Garden under 10 s with the banner and no JSON; guest limits; branded sign-in; problem page; icons and manifest). The rehearsal e2e checks each judge line and claim chip has a caption.

## Phase 2 · Defects found in testing

One migration: `0005_review_phase2.sql` (`repos.capabilities_error`, `coach_notes.not_retested`).

1. **Repo digest HTTP 400 on Muse Wonder.** Three changes, since the cause could not be reproduced without the key. (a) `quoted()` now breaks model special-token syntax in all untrusted text (`<|` and `|>` get a zero-width space), the leading suspect: this repo's own SAM parser contains `<|box;…|>` literals. (b) The capability pass reads up to 400,000 characters of code in batches of 100,000 (one call when it fits), three at a time; results are merged and de-duplicated, and a failed batch does not fail the digest. (c) If every batch fails, the deterministic scan (dependencies, tests, TODOs, secrets, mock responses) is still saved, `repos.capabilities_error` records why, the digest is not cached (so the next run retries), and the repo panel shows "Capabilities unavailable: <reason>" with Retry. Every failed job's reason now includes the API's own error body (first 500 characters), and the worker logs it.
2. **Jobs that lose their UI.** `GET /api/projects/:id/jobs/latest?name=…` returns the project's newest job of a kind (running, queued, or finished in the last hour). The repo, event and winners panels pick it back up on mount and after a failed start request, so a reload or a network blip never hides a running or failed job. The Director reloads its state after any failed request, so a render that did start shows its progress.
3. **First Read repo click ignored.** The button stays disabled while the repo picker is open (a closing Radix Select swallows the next click), while the start request is in flight, and while a digest runs.
4. **Orphan sessions.** The Studio asks for the screen and mic before creating the session, so a blocked capture creates nothing. Realtime records `started_at` when the rehearsal actually starts; rehearsal sessions with no start time older than 5 minutes are deleted (`pruneOrphanSessions`, run when listing and creating sessions), and the Sessions list hides rows that never started. DemoGuard runs are untouched.
5. **EventSpec quotes lost on save.** Saving deleted and re-inserted the criteria with new ids, so the editor could not match them to their quotes until it reloaded. Existing criteria now keep their ids; only criteria the user adds show "Added by you".
6. **Coach Notes "resolved".** An earlier weak spot is resolved only when this session re-checked it and it passed (`passedChecks`): the claim was said again and verified, the criterion was covered (≥ 25 %), the step was re-measured within budget, or a Q&A round had no follow-ups. Anything else that did not come up again is listed as "Not re-tested" and stays in the plan. The seeded earlier note now includes a thin Real-world impact item, which the scripted Demo Mode session covers, so F7's "at least one resolved item" is earned, not assumed.
7. **Cost display.** `modelUseLabel`: "12 model calls, mocked" when no real model ran, "$0.0123 over 7 model calls" when `MODEL_PRICES` covers them, and just the call count when the cost is unknown (never "$0.0000").
8. **Wizard speed.** Step changes are optimistic: the URL changes through the history API (no server round trip), the cached project moves forward at once, and the step is saved in the background. Loading shows a step-shaped skeleton.
9. **Progress page.** `loading.tsx` streams a page-shaped skeleton at once (and a general one for every project page) while the server loads the data.

Tests: special tokens, batching and error reasons (worker), the new resolved rule (ai, worker), model-use labels (shared), and e2e: a failed repo digest shows its reason and Retry and survives a reload (`jobs.spec.ts`); a blocked capture leaves no session row (`guest.spec.ts`). The e2e guest server uses its own build folder (`NEXT_DIST_DIR=.next-guest`), since two `next dev` servers sharing `.next` corrupt each other.

## Phase 3 · DemoGuard fallback playback (browser mode)

One migration: `0006_review_phase3.sql` (`latency_samples.output_frame`).

1. **Stage window** (`/projects/:id/demoguard/stage`, opened from Live control). The presenter shares this window in the call instead of the raw app. It shows the demo window (its own screen capture, display only; Live control keeps its 4 fps capture for detection) and follows DemoGuard over the same `BroadcastChannel` as the cue window. On Fallback (or Recovering) it seeks the clip to the step's in-point (`fallbackSeekMs`) and crossfades in 200 ms, with the Recorded-segment badge unless it is turned off; it cuts back when DemoGuard returns to Live at a step boundary. Freeze pauses the live picture. Setup controls hide once armed (they come back on hover or focus).
2. **The fallback clip** is the golden run's recording: when the project uploads recordings, the step map's `fallback_clip_url` is played from a 6-hour presigned URL; otherwise the presenter loads the local recording file into the Stage window (local recordings never leave the computer). Without a clip, Stage says it is on fallback and to keep narrating.
3. **Keyframes.** Each timed step in a rehearsal stores a 240 px JPEG of its result screen (`thumbnailDataUrl`, re-encoded with `jpeg-js`); a step map built from a golden run copies them into `steps.expected_keyframe_urls`, and Step map shows them. Expected-state detection still compares perceptual hashes (and SAM regions when hosted SAM is on); Phase 4 adds the model check.
4. **Narration** already comes from the golden run's transcript around each step (`deriveSteps`); the generic lines the review saw are the seeded Demo Mode step map's.
5. **OBS** is not built. It is optional in the review and first on its cut list; the companion still logs `obs.switch`.
6. **Test the safety net** (Stage window, when armed): Stage shows a fake error dialog for 4 s and asks Live control to send `demoguard.test`; realtime raises the same critical `error_dialog` signal a real dialog would ("Test of the safety net: an injected error dialog."), so the switch, the incident and the recovery are all real.

Tests: realtime (the test signal switches like a real dialog; thumbnails), shared (keyframes from the golden run), and `demoguard.spec.ts`: the Stage window, loaded with a test-pattern clip, is on fallback within 1.5 s of the switch with the badge, its clip is at the cued in-point, it is back to live after recovery, and Test the safety net switches.

## Phase 4 · Deeper, visible Meta tooling

One migration: `0007_review_phase4.sql` (`projects.pre_pitch_brief`).

1. **SAM 3.1 on screen.** DemoGuard now sends SAM's regions to the browser (`ui.states`), and Live control has a "Watched screen" preview with the labelled boxes and their scores (`RegionOverlay`, shared with the Studio preview). Demo Mode rehearsals use hosted SAM too when Demo Mode runs on the real models: each frame costs three calls from the daily demo allowance (`BudgetedTracker`, `BudgetedLLM.allow`); past it, tracking falls back to hashes and the red-region heuristic. DemoGuard in Demo Mode keeps the local tracker so its scripted scenario stays deterministic. The tracker label is plain words now ("SAM 3.1 tracking (Meta Model API)" or "Basic screen tracking").
2. **Vision in claim verification.** `claimVerify.v2` sends the two shared-screen frames nearest the claim to Muse Spark as images and names their times, so a verdict can cite `frame:m:ss` (v1 always sent `frames: []`).
3. **Muse Spark confirms expected-state mismatches.** When a step's result screen differs from the golden run by hash, DemoGuard asks Muse Spark (`describeFrame`, 3 s timeout) whether the screen shows the step's result with no error. "Yes" completes the step (a cosmetic difference); "no" raises the mismatch with the model's reason; a failed or slow call leaves the hash in charge. Real projects only.
4. **Latency.** Sentences no longer queue behind each other's model calls: each final transcript is handled as it arrives (in order for the transcript and coverage), the judge decision starts alongside claim extraction, and extraction asks for another decision when it adds claims (a decision requested mid-decision runs right after). Claim extraction runs at reasoning effort `minimal` (a per-prompt `effort` overrides the model default). `max` is accepted in the reasoning-effort settings. The 2 s claim-chip target needs measuring on the live deploy with the key (see below).
5. **One Muse Wonder pass for the brief and the bank.** `questionBank.v2` adds to v1's context the event, winning patterns, the written submission, the README, repo capabilities, every session's contradicted and unshown claims, and the last ten Coach Notes, and returns the question bank plus a one-page pre-pitch brief (summary, strengths with evidence, risks, what to say, what to show). The brief is stored on the project and shown at the top of the Q&A Kit with its model caption. pgvector memory stays as an optional cache (no Meta embedding model exists).

**Not built: Muse Voice Transcribe for live speech and Muse Image `/images/edits` for evidence slides.** Both need Meta Model API endpoints whose request and response formats are not in the docs this project has (a realtime ASR WebSocket; an image-edit request with a source image and mask). The build rules forbid guessing endpoints, and both are on the review's cut list. Live speech stays on faster-whisper; evidence slides stay deterministic, verified by Muse Spark vision.

Tests: per-prompt effort and claim-verify images (ai, against recorded replies), the allowance for hosted SAM (ai, realtime), mismatch confirmation yes / no / failure (realtime), the brief's schema and grounding (ai), and the Q&A Kit e2e checks the brief appears.
