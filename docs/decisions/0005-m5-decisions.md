# 0005 — Decisions made while building M5 (DemoGuard)

Date: 2026-10-29. No stack changes. One migration: `0003_m5_demoguard.sql` (`incidents.detection_ms`, `incidents.detail`). Session mode `demoguard` added (text column, no migration needed). The companion now depends on `@stage-ready/shared` and no longer on `obs-websocket-js`.

## Scope: no video

By request, M5 leaves out the video part: no OBS scene switching, no fallback clip playback, no browser-mode full-screen video swap, and no Freeze of the picture. Everything that decides and records a switch is built. When DemoGuard switches, it enters Fallback, tells the companion (`obs.switch`, which it logs), and shows the step and the clip in-point it would cue, with the Recorded-segment badge setting; the cue window tells the presenter to keep narrating. Adding playback later is a consumer of the existing `demoguard.state` and `obs.switch` messages.

## Decisions

1. **State machine as a pure reducer** (`packages/shared/src/demoguard.ts`, table-driven tests). It follows the spec diagram: Idle → Preflight → Armed → Live; Live → Suspect on one non-critical signal (clears after 1 s without another); Suspect → Fallback on a second, different signal within 3 s; Live → Fallback on a critical signal or Panic; Fallback → Recovering when the app looks healthy; Recovering → Live only at the next step boundary; Freeze and Resume; Done after the last step. The same kind of signal twice does not corroborate itself.
2. **Critical signals** are an error dialog or toast, and an HTTP 5xx seen by the companion proxy. Non-critical: request timeout, spinner over budget, step over its maximum duration, blank screen, expected-state mismatch. Each kind is reported once per step so a dialog that stays up does not flood the feed.
3. **Error dialog detection.** With SAM 3.1, its `error_dialog` region (score ≥ 0.5). SAM runs hosted on the Meta Model API when `MODEL_SAM` (`sam-3.1`) and the key are set: `POST /v1/responses`, one phrase per request ("error dialog", "loading spinner", "progress bar") sent in parallel per sampled frame, one frame in flight at a time; the special-token output is parsed for boxes only (masks are skipped). Demo Mode projects keep the local service so they stay deterministic. The pixel heuristic below stays on alongside SAM as a backstop. Without it, a pixel heuristic: the share of strongly red cells on a 64×36 grid rising ≥ 1.2 points above the healthy app's rolling 5 s baseline (and not a mostly red screen). It catches red error banners, toasts and dialogs; neutral-coloured dialogs need SAM. The Live control tab says which mode is active, as the spec asks.
4. **Muse Spark confirmation of an expected-state mismatch is not wired** (the confirmation would add a model call per step on the hot path). A mismatch is a non-critical signal on its own, so it already needs a second signal to switch.
5. **Expected state** is the 256-bit hash of the golden run's result screen (`latency_samples.output_hash`), stored in `steps.success_signal`. No keyframe images are stored: rehearsal frames never leave memory, so the Step map shows whether a step has an expected-state hash rather than a thumbnail. Mismatch threshold: 48 of 256 bits.
6. **Step map from a golden run** (`POST /api/projects/:id/stepmaps`): one step per timed step of that rehearsal, in order. Fallback clip from 1 s before the action to 1.5 s after the result; maximum duration 1.5× the golden run, at least 2 s more and at least 3 s; narration is what was said around the step. Each derive makes a new version; DemoGuard uses the latest. Steps are editable (`PATCH /api/steps/:id`).
7. **Step progress, live:** a step completes when the stopwatch sees its result (the same detector as rehearsals). **On fallback**, steps advance by the clip length (out − in) of each step, so recovery cuts back exactly at the clip's end.
8. **Recovery:** while on fallback, the live screen must show no error, not be blank and, when known, match the step's expected state for 1.5 s.
9. **Frames:** 4 fps, frames only (no audio, no recording), unchanged frames skipped except one per second so a static blank or recovered screen is still seen.
10. **Detection time** is measured from the capture time of the frame that showed the failure (browser clock) to the browser hearing the decision. It shows on Live control and the e2e test asserts it is under 1.5 s. The incident row stores the server-side part (`detection_ms`).
11. **Pre-flight** merges checks from three sources by id: server (step map, SAM, companion), browser (realtime connection, screen shared) and companion (env vars, endpoints and latency, test login, disk). Critical checks that are not `pass` block Arm on the server, not only in the UI. The presenter checklist (Do Not Disturb, sensitive tabs, power) is shown but does not block.
12. **Companion pairing** uses the session's normal 15-minute WebSocket token (`POST /api/sessions/:id/token`); the realtime server accepts connections without an Origin header, so only browsers are origin-checked. Global OS input hooks need native modules and are left out; `signal.input` is accepted if a future companion sends it.
13. **Cue window** follows the DemoGuard page through a `BroadcastChannel` in the same browser, so it needs no second connection or token.
14. **Incidents feed F5 and F7.** A take's demo-success score counts switch and panic incidents in the session the take came from. After a DemoGuard run, `session-review` adds one `incident:<step>` weak spot per failing step to the latest Coach Note (or starts one) and opens a Fix Task (`origin: incident`) per step. DemoGuard runs are left out of rehearsal progress trends.
