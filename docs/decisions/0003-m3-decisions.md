# 0003 — Decisions made while building M3 (Auditor complete, review and memory)

Date: 2026-10-29. No stack changes. One migration: `0001_m3_audit_memory.sql`.

1. **Repo truth check, live.** Deterministic rules run before any model call: a feature claim that shares a distinctive word with a TODO in the code is Contradicted, citing that TODO's `file:line`; a number in a claim that matches a hard-coded value on the demo path (a `mock_response` finding) is Contradicted, citing it, and opens a Fix Task. After the session, the `session-review` job runs a Muse Wonder pass (`sessionAudit.v1`) over claims still Unverified, with repo findings, dependencies, README and submission. A model verdict without evidence never changes a claim.
2. **Show or strike** runs once, when the demo section ends (section change) or at session end. With a vision model, Muse Spark is shown up to three frames taken after the claim (`showOrStrike.v1`); without one, a feature counts as shown if a timed screen step started within 20 s of the claim. Unshown features become Not shown, get the rewrite "Add the step to the demo, or cut the line." and a Fix Task.
3. **Canned-response detector.** Each timed step stores a 256-bit dHash (17x16, decoded server-side with `jpeg-js`) of the screen before the action and of the result (`latency_samples.input_hash`, `output_hash`). Two runs of the same step key, in this or earlier rehearsals, whose inputs differ by ≥ 12 bits but whose outputs match within 3 bits raise a "possible canned response" flag and a Fix Task. The thresholds are calibrated on synthetic frames; adjust them in `auditor/canned.ts` if real demos give false positives.
4. **Cross-source consistency** compares spoken claims with the repo README (now stored on `repos.readme`) and the written submission (`projects.submission_text`, edited in Calibration). A number that disagrees with a sentence about the same thing, or a feature the docs call planned or coming soon, is Contradicted with a `doc` evidence ref. Slides are not compared yet: the presenter's own deck is not ingested (evidence slides arrive in M4).
5. **Honest rewrites** come from measured data where it exists ("It takes about 9.3 s", "under 2.1 s at p95") and otherwise give the honest alternative ("Say offline mode is planned, not built", "Drop the number until an eval measures it").
6. **New WebSocket message** `audit.flag` (M3 addition) for flags that are not claims. Session summaries carry them as `flags`.
7. **Rehearsal Memory.** Weak spots have stable keys (`claim:<text>`, `criterion:<name>`, `slow:<step>`, `qa:vague`, `canned:<step>`) so the `session-review` job can diff them against the previous Coach Note: resolved, still open, new. Muse Wonder (`coachNotes.v1`) writes the three-item plan; the mocked adapter plans from open and new high-severity items, padded with criterion drills, so the plan always has three items.
8. **Memory retrieval.** The Meta API's "Active Memory" is not confirmed, so memory lives in `coach_notes` with a pgvector embedding (when `EMBED_MODEL` is set; OpenAI-style `POST /embeddings`, to confirm in the docs) and is retrieved by cosine distance. Without embeddings it falls back to the most recent notes.
9. **Coach Note items** are now `{key, text, severity}` objects. Notes written before M3 (plain strings) are still read via `toCoachItems`.
10. **Readiness and progress** average coverage over at least the six planned sections, so a criterion only touched in one section does not read as fully covered.
11. **Session review** recordings: uploaded recordings stream through a 15-minute presigned GET; local recordings are opened from disk in the browser and never uploaded. Captions come from the transcript (WebVTT) and are on by default.
12. **Latency chart** budget line uses `DEFAULT_STEP_BUDGET_MS` (2 s) until DemoGuard step maps (M5) set a budget per step.
